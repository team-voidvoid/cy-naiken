# ナイケン（NAIKEN）コンセプト

**預ける前に、内見を。そのサイトに、免許証を預けますか？**

作成: 2026-10-17／対象: OpenAI DevDay 2026 Community Hackathon Tokyo／副題: 預ける前の、Webサービスの内見（英語: A viewing before you move your data in.）／読者: 明日のチームの開発者3人

ナイケン（NAIKEN）は、WebサービスのURLを入れると外から見える範囲だけを読み取り、個人情報を預ける側の利用者に向けて「辛口の一言、気になる点を最大3つ、開くと根拠」の順で診断を出すWebアプリです。デプロイ先は OpenAI の Sites で、公開情報の調査と利用者向けの説明は Agents API の非同期セッションが担い、確定／推測／見えないの分類と採点はコード側が持ちます。当日の公開版は、許可リストにある対象サイトだけを診断します。

---

## 用語

| 語 | 意味 |
|---|---|
| 部品 | フレームワークやライブラリなど、サイトを作っている既製の構成要素です。 |
| 中身年齢 | 検出した部品の公開年やサポート終了からみた、サイトの中身の古さです。 |
| 名乗りすぎ | Server や X-Powered-By などのヘッダで、製品名や版を外に出しすぎていることです。 |
| 確定／推測／見えない | 指摘の3分類です。取得した値で裏づけられた指摘を「確定」、兆候だけの指摘を「推測」、外からは調べられない項目を「見えない」と呼びます。確定は観測事実の確定で、安全性や被害の確定ではありません。 |
| 速報 | 観測が終わった直後に出す結果です（受付から最大20秒）。公開設定（ヘッダ、Cookie属性、HTTPS）の判定と検出した部品を含み、中身年齢は「照合中」と出します。受付直後の画面は「受付中・取得中」です。 |
| ターンAとターンB | Agents API の同じセッションで使う2つのターンです。ターンAは部品の公開日と保守状況の照合、ターンBは Sites が選んだ指摘の文章化です。それぞれの turn_id を D1 に保存します。 |
| CSP | Content Security Policy。ページで実行してよいスクリプトの出所をブラウザに指示する設定で、HTTPヘッダかHTMLのmetaで書きます。 |
| EOL | End of Life。公式のサポートや保守が終わった状態です。 |
| SSRF | Server-Side Request Forgery。任意のURLを取得するサーバを使って、内部ネットワークやクラウドの内部情報用アドレスに通信させる攻撃です。 |
| CSRF | Cross-Site Request Forgery。利用者の意図しない送信を別サイトから起こす攻撃で、フォームに埋めたトークンで防ぎます。 |
| 許可リスト | 当日の公開版で診断を受け付ける対象（ホストと、必要なら明示したパス）と、JS の配信先ホスト（code.jquery.com や cdnjs.cloudflare.com などの CDN を含む）の一覧です。D1 に置き、チームが足せます。 |
| Seasar2 | 2016年9月26日にサポートが終わった日本製の Java フレームワークです。古い部品の例に使います。Teeda はその上で動く画面用の部品です。 |
| Wayback Machine | Internet Archive が運営する、過去のWebページの保存サービスです。 |
| DevDay | OpenAI の開発者向け発表イベントです。発表された機能を使うことがハッカソンの条件かどうかは、公式ページでは確認できていません（12章）。 |
| Sites | OpenAI の Codex が作った Web アプリを、OpenAI がホストして URL で出す機能です（プレビュー）。実行環境は Cloudflare Workers 互換で、表形式のデータは D1、ファイルは R2 に保存します。 |
| Agents API | OpenAI 側で実行と対話の状態管理を行い、Webアプリから呼び出せる AI エージェントの API です。セッションを非同期で実行し、完了を Webhook で通知できます。マネージドAgent とも呼びます。 |
| ホスト型サンドボックス | Agents API の実行環境の一つで、Node.js や Python が動き、外向きの通信ができます（公式資料の記述で、実動作は未検証）。 |
| computer_use | Agents API のツールで、OpenAI がホストするブラウザを Agent が操作します。 |
| Webhook | 処理の完了などを、相手のサーバの URL に HTTP で通知する仕組みです。 |
| dot | 調査と文章化を任せる候補の名前です。公開Webアプリから自動で呼び出せるかは未確認です。 |
| Decisions API | OpenAI の API で、与えた材料から条件判定や基準に沿った点数を速く返します。 |
| Retire.js | 既知の古いJSライブラリを、ファイル名やファイルの中身から見つけるオープンソースの道具です。 |

## 1. コンセプト

画面は利用者（個人情報を預ける側）向けの1種類です。利用者向けの説明を最上段に出し、その下を開くと開発者にも確かめられる根拠が見える構成にします。

ナイケン（NAIKEN）は、WebサービスのURLを入れると、外から誰でも見られる範囲（対象ページのHTML、HTMLが直接参照するJS、レスポンスヘッダ、Cookie属性）だけを読み取り、「そのサイトに、免許証を預けますか」という問いに利用者が自分で答えるための材料を出す診断アプリです。名前は、部屋を借りる前に中を確かめる「内見」から取りました。コピーは「預ける前に、内見を。」、副題は「預ける前の、Webサービスの内見」、英語の副題は "A viewing before you move your data in." とします。副題で Web サービスの話だと示し、不動産の内見ツールと区別します。

診断の柱は3つです。

1. 使われている部品とバージョンを検出し、EOL や公開日からの古さで中身年齢を出します。
2. IPA「安全なウェブサイトの作り方」の基本から外れていそうな箇所（CSP の不在、Cookie属性の不足、HTTPS の不備など）を、表面に出ている範囲で指摘します。
3. すべての指摘を確定／推測／見えないに分け、根拠（実際に取得した値と出典）を並べます。

## 2. 解決したい課題

見た目がきれいで有名なサービスでも、裏側が更新されているとは限りません。利用者は中身を知らないまま、住所や免許証などの大事な情報を預けています。専門家なら気づく「サポート終了した部品」「古いままのライブラリ」「防御設定の不足」を、登録する前と使い続ける前に、誰でも確かめられるようにします。

## 3. 利用イメージ

1. 利用者がURLを入れます。アプリは入力を許可リストに登録した URL（ホスト、または明示したパスまで）に正規化し、「このページを調べます」と表示します。ルートは拒否されて特定のパスだけ取得できる対象（CoCo壱番屋の注文ページ。13章）があるので、オリジンだけに揃えません。当日の公開版は許可リストにあるサイトだけを受け付け、それ以外には「このサイトはまだ診断できません。会場で声をかけてください」と出します。
2. 受付直後は「受付中・取得中」と出し、観測が終わると速報が出ます（受付から最大20秒）。公開設定（ヘッダ、Cookie属性、HTTPS）の判定と検出した部品が並び、中身年齢は「照合中」です。調査の間は、何を調べているか（公式の公開日と保守状況の照合、説明の作成）を画面に出します。画面を閉じても、開き直せば続きから進みます。
3. 調査が終わると、辛口の一言と、気になる点（最大3件）が利用者の言葉で出て、中身年齢が入ります。気になる点は0〜2件でも完成で、穴埋めの指摘は作りません。
4. 各項目を開くと、検出した値と出典（公式の公開日や保守状況の告知）が見えます。
5. 取得できなかった場合（アクセス拒否、時間切れ）や、調査が時間内に終わらなかった場合、AI の文章が根拠と合わなかった場合も、理由を書いた画面か定型文を出します。速報だけでも画面は成立します。Bot対策のチャレンジページや 403 が返ったときは「取得を拒否された」として扱い、その応答のヘッダは通常ページの設定として採点せず、拒否を危険度の点数にも使いません。確認できた項目と確認できなかった項目を分けて出します。

## 4. 診断の見せ方

看板は「2016年製の部品が、今も現役。」のような一言で、その直下に「jQuery 1.12.4（2016年5月公開）を検出」のような事実を置きます。一言は、検出した事実から言えることだけで作ります。見た目が新しいかどうかは利用者が自分の目で見ているので、アプリは裏側の事実を言い、見た目との落差は利用者に委ねます。古さは、検出した最古の部品の公開年で言います。部品一つの古さを、サイト全体の年齢と区別して伝えるためです。

一言と根拠の対応は次のとおりです。

| 一言 | その下に出す根拠 |
|---|---|
| 2016年製の部品が、今も現役。 | 検出した部品、バージョン、公開日、出典URL |
| この部品、公式サポート終了から10年。 | Seasar2 のサポート終了日（2016年9月26日）の告知と、Teeda 由来の公開ファイルの検出根拠。「Teeda 由来のファイルがある」ことと「今のサーバで Seasar2 が動いている」ことは分けて表示します |
| サーバの製品名と版が、丸見えです。 | Server と X-Powered-By ヘッダの値 |
| CSP による追加の実行制限は確認できません。 | レスポンスヘッダと HTML の meta の一覧 |

画面の構成は次の6つです。

- 速報。観測の直後に、公開設定の判定と検出した部品を出し、中身年齢は「照合中」と出します
- 一言と、気になる点（最大3件。利用者向けに AI が書き、選ぶのは点数順でコードです。0〜2件でも完成とし、穴埋めの指摘は作りません）
- 中身年齢と、検出した部品の年代と公式の保守状況（非推奨化や保守方針を含む）。運営の保守実態まで示唆する「放置気味」「化石化」のようなバッジは出しません
- 指摘一覧。確定は重く、推測は軽く採点し、見えないは採点の対象外です。「確認できた範囲」（5項目中いくつ確認できたか）を併記し、点数を確認できた項目の数と一緒に読めるようにします。確定は観測事実の確定で、安全性や被害の確定ではありません
- 見えない項目。SQLインジェクションなどサーバ内部の安全性は「この点検では分かりません」と必ず表示します
- 根拠。検出した値、出典URL、取得日時、照合日時、表示日時。公開するのは根拠に必要な部分（部品と版、ヘッダ名と判定に使った値、Cookie の名前と属性、出典URL）だけです

## 5. 取得の範囲と検出項目

取得は、対象ページ（既定はトップページ、許可リストでパスを明示した場合はそのページ）の HTML（https と http の2回）と、HTML が直接参照する JS です。JS は当日3〜5本から始めて実測で増やし、天井は20本です。取る順番は HTML の並び順ではなく、ファイル名や URL にライブラリ名や版が入っているもの（jquery、swiper など）と、同じホストの /js/ 配下を優先します。上限で取れなかった参照は「未取得」として本数を残し、未取得の部品を「存在しない」とは扱いません。ふるさとチョイスでは script 14個のうち jQuery が7番目、Swiper が12番目で、先頭から3〜5本では根拠を取りこぼします（13章）。リダイレクトは各取得につき3回までで、HTML 2回と JS 20本に各3回のリダイレクトがつくと HTTP 要求は最大88回になるので、総通信回数、合計サイズ、合計時間をまとめて上限にします。仮の値は、合計10MB、取得全体で20秒です（Sites の実行時間と通信回数の上限が未確認なので、当日実測して決めます）。取得はこの範囲で完結し、JS は中身を読むだけです。

当日の公開版は、対象ホストと JS の配信先ホストを許可リストで絞ります。任意の URL を受け付けるのは、安全な取得経路を検証できてからです（8章、11章）。

JS を取る理由は、URL に版が出ていないライブラリでもファイルの中の版表記から検出できるからです。実測では、https://code.jquery.com/jquery-1.12.4.min.js の先頭は `/*! jQuery v1.12.4 | (c) jQuery Foundation` でした（2026-10-17 取得）。

検出項目は次の5つです。

1. セキュリティ関連の HTTP ヘッダ（CSP、X-Frame-Options と frame-ancestors、HSTS、nosniff、charset）。CSP は HTML の meta にも書けるので、ヘッダと meta の両方を見ます（MDN の CSP の説明 https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CSP ）。Report-Only は実際の制限と区別します
2. Cookie属性（Secure、HttpOnly、SameSite、有効期限）
3. HTTPS（リダイレクト、混在コンテンツ、http 宛てのフォーム）
4. 名乗りすぎと古い部品（Server と X-Powered-By、generator、古い JS ライブラリ、HTML の属性や meta にある版表記）。styled-components の `data-styled-version` のように HTML だけで版が分かる部品もあり、`__NEXT_DATA__` のように技術名だけ分かる手掛かりもあります（13章）。`<meta name="version">` はアプリ側の版として別に記録し、ハッシュ状のファイル名や buildId は版には使いません。中身年齢の材料です
5. POST フォームの CSRF トークンらしきもの（推測の見本として1つだけ）

判定の根拠は IPA「安全なウェブサイトの作り方」第7版の第2章（PDF https://www.ipa.go.jp/security/vuln/websecurity/ug65p9000001971s-att/000017316.pdf ）で、HTTPS、HSTS、セッション Cookie の Secure はここに拠ります。誤判定になりやすい点は次の5つで、判定ルールに織り込みます。

- CSP が無いことは XSS があることを意味しないので、「CSP による追加の実行制限は確認できません」にとどめます
- CSRF トークンが HTML に無いことは対策が無いことを意味しないので、推測の扱いにします
- HttpOnly と SameSite=Strict は、すべての Cookie には求めません。求めるのはセッション Cookie の Secure です
- meta に書いた CSP では frame-ancestors が効かないので、クリックジャッキングの判定は X-Frame-Options かヘッダの CSP で見ます
- IPA の CSP の設定例は古いので、推奨値としては使いません
- 取得を拒否された応答（403 など）のヘッダは通常ページの設定として採点せず、拒否の原因（海外 IP、Bot 対策、User-Agent、TLS）も決めつけません。事前調査では同じ URL でも取得環境によって 403 と 200 が分かれました（13章）
- HTML が取れたことと画面が描画されたことは分けます。`<div id="__next"></div>` が空のように、表示に JS の実行が要る構成があります。外部 JS の参照が無いことだけで JS 不要とは決めません

観測から言えることと言えないことの線は、次の表のとおりです。

| 観測 | 言えること | それだけでは言えないこと |
|---|---|---|
| HTML に http: の参照がある | http 形式の参照が記載されている | 実際に平文で通信した。ブラウザや CSP の upgrade-insecure-requests が HTTPS 化やブロックをする場合があります |
| HTTPS の応答に HSTS が無い | 今回の応答で HSTS ヘッダを確認できない | 保存済みの HSTS、親ドメインの指定、preload も無い |
| 期限の無い Cookie | ブラウザの保存期間上のセッション Cookie | ログイン管理用の Cookie である |
| 用途不明の Cookie に Secure が無い | その Cookie に Secure 属性が無い | 認証情報が漏れると確認できた |
| CSP ヘッダがある | ポリシーが記載されている | スクリプトの出所が制限されている。upgrade-insecure-requests だけの場合があります |
| CSP が Report-Only だけ | 報告用の設定がある | ブロックが強制されている |

出典は MDN の Mixed content（ https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Mixed_content ）、upgrade-insecure-requests（ https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/upgrade-insecure-requests ）、HSTS（ https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Strict-Transport-Security ）、Set-Cookie（ https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie ）、CSP（ https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy ）です。

取得は固定したヘッダで新規のリクエストを作り、利用者のブラウザから受けた Cookie や Authorization を対象サイトへコピーしません。リダイレクトは手動で1回ずつ検査し、別ホストへヘッダを転送しません。Cloudflare は自動追従のときに別ホストへもヘッダを転送すると注意しています（ https://developers.cloudflare.com/workers/runtime-apis/request/ ）。

部品の検出結果は「技術名が分かる」「版まで分かる」「何も特定できない」の3段階で持ちます。版が分からなくても、ヘッダ、Cookie属性、HTTPS は取得した応答から確認できるので、結果は「中身年齢: 判定材料不足／公開設定: 3項目確認」のように出します。Retire.js は署名データ（JSON）だけを取り込んで補助に使います。結合や加工をされたファイルは元ファイルのハッシュと一致しないので、内容の特徴やライセンス表記で拾える場合もある、という扱いです。

公開日と EOL 日は別のデータとして持ちます。公開日は npm の登録情報で引きます（例: https://registry.npmjs.org/jquery に jQuery 1.12.4 の公開日時があります）。EOL 日は、手書きの EOL 表（Seasar2 と Teeda は公式告知 https://www.seasar.org/ の2016年9月26日）と、endoflife.date の現行 API v1（例: https://endoflife.date/api/v1/products/jquery/ ）で引きます。endoflife.date に Seasar2 と Teeda はありません。jQuery は EOL が true、EOL 日が null、isMaintained が true と同時に返り、isMaintained は商用サポートを含む指標なので、それだけで「公式サポート中」とは判定しません。EOL 日が分からない部品は「2016年公開の版、公式サポート終了済み」のように書き、「終了から何年」は EOL 日が確認できた部品にだけ使います。保守状況は「公開日」「EOL 日」「非推奨化」「保守方針」を別の欄で持ちます。jQuery Mobile の公式表現は fully deprecated なので「非推奨化」として記録し、宣言された EOL 日とは同一視しません。jQuery 3.x は重大な修正に限る保守方針なので、3.x 全体を EOL とは呼びません。styled-components は2026年の公式記事で開発継続が明記されているので、古い版が見えても「その版の EOL は確認できない」と書きます。デモで使う部品の公式の公開日と保守状況は13.6 にまとめ、手書きの EOL 表の初期内容にします。検出できても未確認の欄は推測で埋めません。

### 5.1 ヘッダ点検の参考コード：Agentic-SEO-Skill

[Bhanunamikaze/Agentic-SEO-Skill](https://github.com/Bhanunamikaze/Agentic-SEO-Skill) を、ヘッダの取得・点検部分の参考候補として残します。元の用途は SEO の総合監査で、広いクロールや PageSpeed の確認も含むため、ワークフロー全体は取り込みません。

- [scripts/security_headers.py](https://github.com/Bhanunamikaze/Agentic-SEO-Skill/blob/main/scripts/security_headers.py)：GET で得た応答の HSTS、CSP、X-Frame-Options、X-Content-Type-Options（nosniff）、Referrer-Policy、Permissions-Policy を点検し、JSON で結果を出す部分が参考になります。ヘッダの有無や既存の評価を、そのままサイト全体の安全性やナイケンの点数には使いません。本文の誤判定対策と、確定／推測／見えないの分類を優先します。
- [scripts/lib/safe_http.py](https://github.com/Bhanunamikaze/Agentic-SEO-Skill/blob/main/scripts/lib/safe_http.py)：リダイレクト、TLS 証明書の検証、タイムアウト、応答サイズの制限を読む参考です。このコードを参照するだけで SSRF 対策が完成するとは扱わず、5章と8章の取得範囲・許可リスト・制限を維持します。

このヘッダ点検スクリプトは、技術名・バージョンの検出、公開日・EOL の照合、Cookie 属性の診断を代替しません。Python コードが Sites 上でそのまま動くかは未検証なので、採用する場合も必要な処理だけを既存の取得経路に合わせて検討します。[SKILL.md](https://github.com/Bhanunamikaze/Agentic-SEO-Skill/blob/main/SKILL.md) は元の用途の確認用です。[LICENSE](https://github.com/Bhanunamikaze/Agentic-SEO-Skill/blob/main/LICENSE) は MIT で、コードを再利用する場合は著作権表示と許諾文を保持します。現時点では参考先の記録のみで、導入・実行・採用はしていません。

## 6. AI の役割と処理の流れ

処理の順序は「観測、速報、照合（ターンA）、採点と指摘の選択、文章化（ターンB）、検査」です。古さの点数は照合が終わるまで確定できないので、照合を採点より先に置きます。確定／推測／見えないの分類と採点はコードが持ち、AI は照合と説明を担います。再現性を固定する単位は、観測、照合に使った資料、ルールの版、基準日の4つで、同じ HTML でも EOL の資料や照合結果が変われば点数は変わります。

1. 観測（Sites、コード）。受付のリクエストの中で、許可リスト内の対象を取得し、ヘッダ、Cookie属性、JS、検出した部品名と版を観測事実としてまとめ、D1 に保存します。
2. 速報（Sites、コード）。公開設定の項目（ヘッダ、Cookie属性、HTTPS）を確定／推測／見えないに分類して仮の点数を付け、検出した部品と一緒に画面へ返します。
3. 照合（Agents API のセッション、ターンA）。観測事実を入力として渡し、検出した部品の公式の公開日と保守状況を出典URL つきで調べます。Agent は対象サイトを取り直さず、渡された観測事実だけを使います。確定にする条件は、出典URL があることに加えて、製品、版、日付が出典の本文と一致することです。一致しない項目は推測扱いにし、中身年齢の計算には確定の項目だけを使います。
4. 採点と指摘の選択（Sites、コード）。ターンAの成否と出力の形式を確認してから、固定ルールで分類と点数を確定し、説明する指摘を点数順に最大3件選びます。採点の関数は調査・診断担当が1つのモジュールとして書きます。
5. 文章化（同じセッションのターンB）。選んだ指摘だけを渡し、利用者に関係する意味まで言い換え、辛口の一言を書きます。たとえば「古いライブラリを検出しました」を、「見た目は新しくても、使われている部品には長く更新されていない兆候があります。個人情報を登録する前に、知っておきたい点です」まで言い換えます。
6. 検査（Sites、コード）。文章が、選んだ根拠の ID、製品名、版、日付と一致するか、選んでいない指摘が混ざっていないかを確かめます。合わなければ定型文を表示します。外部ページ、JS のコメント、出典の本文に書かれた命令は資料として扱い、実行の指示にはしません（OWASP のプロンプト注入対策 https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html ）。意味まで踏み込んだ高度な点検だけを余力枠にします（11章）。

照合と文章化は Sites の HTTP 接続にぶら下げず、Agents API の非同期セッションで動かします。Sites はセッションを開始し、セッション ID と、ターンAとターンBそれぞれの turn_id を D1 に保存して、別のターンの出力を混同しないようにします。公式仕様では、idle 中への入力は新しいターンを始め、実行中の入力は現在のターンを操舵するので、ターンAの成功を確認してからターンBへ進みます（セッション https://developers.openai.com/api/docs/guides/agents-api/sessions 、イベントと保存済み項目 https://developers.openai.com/api/docs/guides/agents-api/sessions/events ）。画面は短い間隔で状態を照会し、最初は、照会のたびに Sites が Agents API にセッションの状態と結果を取りに行く形で完成させます。Webhook での完了通知は、それが動いてから足します。Sites で外部からの Webhook を受けられるかは実機で確かめるまで分からないからです。D1 に状態を保存するだけでは Sites 側で処理が裏で走り続けるわけではないので、非同期の実行は Agents API 側に置きます。

複数の閲覧者が同時に状態照会してもターンBを二重に始めないように、D1 の条件付きの状態更新で送信担当を1つにします。送るメッセージの論理キーと内容を送信前に保存し、結果が分からない再送には同じ Idempotency-Key と同じ内容を使います（公式の入力再送の方式。メッセージ投入の仕様で、セッション作成にも同じ保証があるとは扱いません）。全員が画面を閉じると、ターンAは非同期に続きますが Sites の採点とターンBの開始は次回の照会まで止まるので、MVP は「再表示時に続きから進む」仕様にします。画面を閉じても無人で最終診断まで進める要件は、Webhook などの再開の契機を足してからです。

セッションが idle になったことや処理が終わったことだけでは成功とみなしません。対象のターンの成否と、結果が決めた形式になっているかを取り直して確かめます。進捗の状態には「入力待ち」「採点中」「採点保留」も入れます。

AI の本命は Agents API です。公式資料（ https://developers.openai.com/api/docs/guides/agents-api/overview 。非同期のセッション実行 https://developers.openai.com/api/docs/guides/agents-api/sessions と Webhook 通知 https://developers.openai.com/api/docs/guides/agents-api/sessions/webhooks ）があるので、調査・診断担当が入出力の形とプロンプトを前日から準備できます。当日の DevDay の発表で有利な機能があれば、AI 側の中身だけを差し替えます。dot は、公開 Web アプリから自動で呼び出せるかを確認できたときの差し替え候補です。当日に実装時間が足りないときは、固定ルールで確認できた項目だけを採点し、残りは「採点保留」と表示します。AI に項目ごとの判定を任せる採点は、「同じ条件なら同じ点数」と両立しないので作りません。作る場合は方式を明示し、再現性の保証を分けます。

AI との受け渡しの形は、当日 14:00 の工程で固定します。ターンAの入力は観測事実（取得日時、取得状態、取得条件（最終 URL、HTTP ステータス、本文サイズ、本文のハッシュ、User-Agent）、取得した参照と未取得の参照、ヘッダ、Cookie属性、部品と版、根拠の値、速報の分類）、出力は照合結果（部品ごとの公開日、EOL 日、非推奨化、保守方針、出典URL、一致の可否）です。ターンBの入力は Sites が選んだ指摘（根拠の ID、分類、点数、根拠の値）で、出力は文章（一言、各指摘の説明、分からなかったこと）です。Agent の呼び出しが失敗したり時間切れになったりしても、速報だけで画面が成立するようにします。

代案として、観測（取得と部品検出）もホスト型サンドボックスの中で行い、Sites を画面と受付に集中させる構成があります。Sites の実行時間や通信回数の上限に当たったときの逃げ道で、実動作は未検証です。Agent の computer_use（OpenAI がホストするブラウザ）で実際にページを開く調査は、今回の観測手段としては未検証で、新しいオリジンを開くたびに利用者の承認が要って画面に承認の導線が増えるので、後回しにして将来の案にします（11章）。

Decisions API は、速報の分類や定型文の選択に役立つと当日確認できたときに、追加機能として入れます。自由文の一言を直接作る API ではないので、使うなら分類と定型文の選択に限ります。速報はコードのテンプレートだけでも出せます。

## 7. 既存サービスとの違い

違いは機能の有無ではなく、利用者が個人情報を預ける前に、古さと根拠を分かりやすく読める体験です。部品ごとには既存サービスがあります（技術検出は Wappalyzer と BuiltWith、ヘッダ診断は securityheaders.com と Mozilla Observatory、古い JS は Retire.js、国内の無料スコアは Spider AF SiteScan、EOL 検出つき格付けは UpGuard など。research/similar-services.md に出典があります）。Wappalyzer は版番号も検出し（ https://www.wappalyzer.com/docs/fields/ ）、Spider AF SiteScan には設定の点検と AI によるリスクの説明があります（ https://jp.spideraf.com/sitescan ）。比較で言うのは次の3点です。

1. 誰のためか。既存は運営者、開発者、企業のリスク管理向けです。ナイケンは個人情報を預ける側のものさしです。
2. 何を読ませるか。部品の版と EOL と公開日から中身年齢と公式の保守状況を出し、利用者の言葉で意味まで説明します。
3. 見せ方。確定／推測／見えないを根拠つきで分け、辛口の一言と1画面で出します。

> 「securityheaders.com は鍵がかかっているかを見る。Wappalyzer は何で建っているかを見る。ナイケンは、住む前の内見のように、その家が築何年で、もう修理してもらえない部品が使われていないかを、住む人向けに一言で言う。」

## 8. やらないこと（倫理・安全）

**攻撃しない。** パスの総当たり（`/.git`、`/admin` など）、エラーを誘発する入力、フォーム送信、ログイン試行、ポートスキャン、脆弱性の実証、大量リクエストはしません。対象への取得は5章で決めた範囲（HTML 2回と JS 3〜5本、天井20本、許可リスト内）だけです。

**自分たちのアプリも守る。** 当日の公開版は、対象ホストと JS の配信先ホストを許可リストで絞ります。Workers が内部ネットワークに届かないことは Sites の保証として確認できていないので、実行環境に頼らず入口で絞ります。許可リストの中でも、入力URL、リダイレクト先、JS の取得先のすべてで、スキームは https と http だけを通し、IP リテラル、localhost、内部向けのホスト名は拒否し、リダイレクトは自動で追わずに1回ずつ検査します（OWASP の対策指針 https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html ）。応答サイズ、回数、時間の上限も設けます。取得は固定したヘッダで新規のリクエストを作り、利用者のブラウザから受けた Cookie や Authorization を対象サイトへコピーしません（5章）。Agent には取得済みの観測事実を渡し、対象サイトを取り直させません。任意の URL を受け付けるのは、安全な取得経路を検証できてからです。

**同じ対象への取得はまとめる。** 対象の単位は正規化した URL（許可リストの項目）で、同じホストでも別のパスは別の対象です。受付で重複実行を防ぎ、進行中の同じ対象には同じ診断 ID を返します。結果は D1 に一定時間保存して再利用し、利用者ごと、対象ホストごと、アプリ全体の回数上限は受付で設けます。Agent が調べた部品の公開日や EOL も保存して再利用します。

**公開するのは根拠に必要な部分だけ。** アプリと結果ページは公開し、一覧に載せるのは最初はチームが選んだデモ結果だけです。結果ページに出すのは、部品と版、ヘッダ名と判定に使った値、Cookie の名前と属性、出典URL です。取得した生の HTML、Cookie の値、Agent のログは公開しません。一覧は診断日時順に並べます。順位づけやワーストランキングは作らず、サイト名を挙げる集計は「CSP 未設定は診断の62%」のような数字と、褒める方向だけにします。サイトの運営者から削除の依頼があれば、その結果ページを消します。

**断定しない。** 推測は「可能性」「らしき」と書き、ヘッダが揃っていても「安全」とは言いません。出典URL があるだけでは確定にせず、製品、版、日付が出典の本文と一致したものだけを確定にします。確定は観測事実の確定で、安全性や被害の確定ではありません。AI の出力は、選んだ根拠との一致を検査してから（6章）、根拠と並べて表示します。

**Cookie は名前と属性だけを扱う。** 値は読み捨てます。

**ハッカソンのルール。** 実装は当日 Codex で行います（Claude Code は不可）。事前に用意するのはコンセプト、名前、設計資料までです。成果物は Web 公開します。デプロイ先は OpenAI の Sites で、公開設定はパブリックにします。

## 9. 当日の体制と作る順番

3人を「画面」「受付・進捗管理」「調査・診断」に分けます。受付・進捗管理が画面と調査をつなぐ担当で、Agents API の非同期セッションの開始、状態照会のたびのセッションの状態と結果の取得、ターンAの成否確認と採点の呼び出し、ターンBの開始、D1 への保存を持ちます。Webhook の受信は、状態照会で一通り動いてから足します。受付担当がダミーの調査処理を先に用意すれば、調査担当の完成を待たずに画面まで一度つながります。採点の評価基準と AI の説明文は同じ人（調査・診断）が持ち、点数と言葉を揃えます。企画と発表を持つ人が調査・診断を兼ねる案を推します。どんな診断なら刺さるかを、ルールとプロンプトに直接反映できるからです。

| 担当 | 作るもの | 完了条件 |
|---|---|---|
| 画面 | URL 入力、速報の表示、調査中の進捗表示、診断結果、根拠の展開表示、取得失敗と時間切れと許可リスト外の画面、一覧ページ | 仮データで一通りの画面が動く。受付の API につなぐと公開 URL で入力から診断までが通る |
| 受付・進捗管理 | 診断 ID の発行、入力の検査と許可リストの照合、重複実行の防止、回数制限、観測と速報の呼び出し、D1 への保存、Agents API のセッション開始、状態照会のたびのセッションの状態と結果の取得と保存（ターンの成否と結果の形式の確認、セッション ID と turn_id の保存を含む）、ターンAの成功後の採点の呼び出しと指摘の選択、ターンBの開始（条件付きの状態更新で二重起動を防ぎ、再送は同じ Idempotency-Key で）、再表示時の再開、Webhook の受信（動いてから追加）、Sites への統合とデプロイと公開 | URL を受け付けると診断 ID が返り、状態照会で速報と進捗が、完了後に結果が返る。2画面で同時に照会してもターンBが二重に始まらない。統合と公開の責任者 |
| 調査・診断 | 許可リスト内の安全な取得（URL 検査、固定ヘッダ、リダイレクトの検査、上限）、部品名と版の抽出（script の URL、JS ファイル先頭の版表記、HTML の属性、Retire.js の署名データ）、公開設定の判定と速報の分類、手書きの EOL 表（13.6）と endoflife.date と npm の照合、採点の関数と指摘の選択、採点保留の扱い、ターンAとターンBのプロンプトと出力の形、AI 出力の検査（根拠との一致）、Decisions API の採否 | 観測事実のサンプルを渡すと、照合結果、採点、文章が決めた形式で返る。取得と部品検出は単体で試せる |

最初の15分で全員で決めることは4つです。調査へ渡す入力（観測事実。取得条件と未取得の参照を含む）の形、進捗の状態の形（受付済み、取得中、速報済み、照合中、採点中、採点保留、文章化中、入力待ち、完了、失敗）、完成結果（照合結果、採点、文章）の形、共通サンプル3種類（古い部品あり、版不明、取得拒否）です。

| 時間 | やること |
|---|---|
| 14:00〜14:15 | データの形とサンプルを固定する。受付担当は空のまま Sites に保存してデプロイし、公開 URL を用意する |
| 14:15〜14:45 | 3人並行。受付担当はダミーの調査処理で画面までつなぎ、調査担当は下の確認順の2と3（Sites からの取得、Agents API の小さい照合ターン）を最初に通す |
| 14:45〜15:30 | 実際の取得、速報、ターンAとターンBに差し替える。デモ対象のサイトを許可リストに入れて初回確認をする |
| 15:30〜16:15 | 実データで統合する。待ち時間、失敗、状態照会と結果の取得、二重起動の防止、再表示時の再開、キャッシュを確認する |
| 16:15〜17:00 | 機能追加を止め、公開環境でテストと見せ方の調整をする |
| 17:00〜17:30 | デモ練習。取得日時つきの保存済み結果も準備し、凍結する |

最大の不確定要素は画面ではなく、安全な取得と、Agents API のアカウント権限と実際の待ち時間です。14:15 からは次の順に確かめます。

1. 公開 URL を未ログインの環境で開き、画面とサーバの API が動くこと。
2. Sites から候補1件の HTML と少数の JS を取得し、HTTP ステータス、サイズ、タイムアウト、Cookie属性の扱いを確認すること。拒否の応答は採点しないこと。
3. Agents API の小さい照合ターンを1回通し、権限、モデルの可用性、待ち時間、保存した turn_id での結果取得を確認すること。
4. ターンA、Sites の採点、ターンBを通すこと。2画面で同時に照会しても二重に始まらないこと、閉じて再表示したときに再開すること。
5. 「拒否」「版不明」「指摘1件」「AI 失敗」「不正な出力形式」の5つで表示が成立すること。

この5つが通るまでは、Webhook、dot への差し替え、別の採点の実行経路を増やしません。

守るものは「URL 入力、速報、一言と気になる点（最大3件）、根拠を開く」の一往復です。時間が足りなければ、Decisions API、一覧ページ、部品の保守状況の表示、採点の一部（保留にする）の順に削ります。

仕事は調査・診断に集中するので、取得と検出の項目を絞り（許可リスト、JS 3〜5本）、画面担当は一通り完成したら結果表示のテストと説明文の点検を手伝います。安全な取得の制限は調査・診断が、受付時の回数制限は受付・進捗管理が持ち、責任を分けて抜けを減らします。

Codex には担当範囲と共通データ形式を渡し、別ブランチと別の作業場所で進めます。共通の型と依存パッケージの変更は受付・進捗管理担当に集約します。取得は fetch を基本にし、Node 固有の接続制御や DNS の固定に依存しません。Cloudflare Workers の node:http は fetch ベースで、Agent は接続プールなどを提供しない代替品です（ https://developers.cloudflare.com/workers/runtime-apis/nodejs/http/ ）。Sites 互換の設定は当日実測します。URL 検査は自分たちで書きます。

デプロイ先は OpenAI の Sites で、公開設定はパブリックにして誰でも開ける URL にします。ドメインは Sites のデフォルトのドメインをそのまま使います。保存で候補の版を作り、デプロイで本番 URL に出す2段階なので、本番 URL への反映は受付・進捗管理担当が一人で持ちます。OpenAI の API キーは Sites の設定画面で管理します。

### 13.5 当日の候補の選び方と、仕様への持ち帰り

まずは、次の組み合わせを試す案です。採用は当日の Sites からの取得と根拠の保存を確かめてから決めます。

1. 部品の版表記が見える例：CoCo壱番屋、オリックス、ふるさとチョイスから1件。
2. 一部の版が見えない例：KFC、またはほっともっと注文サイト。取得できた項目と材料不足の項目を並べて見せます。
3. 取得が拒否される例：マツキヨココカラ。ただし拒否状態が変わる可能性があるため、実際の取得日時と取得条件を付けた保存結果も用意します。

オリジンだけに揃える入力・取得の想定では、CoCo壱番屋の `/coco-to/` のような対象をそのまま扱えません。この観測を受けて、3章と5章の入力の正規化は「許可リストに登録した URL（ホスト、または明示したパス）」に変え、対象の単位と保存単位も正規化した URL にしました（反映済み）。リダイレクト先と JS 配信先の許可範囲は8章のとおりです。任意 URL の取得範囲を広げることは別の検討です（11章）。

取得失敗では空の画面にせず、「この取得条件では確認できませんでした」「確認できた項目」「確認できなかった項目」を分けて出す想定です。拒否ページを通常ページとして採点しません。公開 HTML の情報だけでは分からない点を、AI が推測で埋めないようにします。

このメモには認証用 URL フラグメント、Cookie の値、ログイン情報を載せません。前日の作業は候補の調査と記録までで、アプリの実装や当日の取得成功を確認済みとするものではありません。
